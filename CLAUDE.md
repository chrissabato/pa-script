## Commands

- Install deps: `composer install`
- Config: copy `.env.example` to `.env` (gitignored) — DB credentials + `IMPORT_TOKEN`. Production reads DB credentials from the server's shared `/www/athletics.willamette.edu/creds.pgsql.json` (`DB_CREDS_FILE`) and keeps its tables in their own schema of that shared database (`DB_SCHEMA=pa_script`; `App\Database\Config`, used by both the app and Phinx, which creates the schema on first run). Dev uses the `DB_*` vars and `public`.
- Migrations: `vendor/bin/phinx migrate -c config/phinx.php` — the config lives at `config/phinx.php`, **not** the default `phinx.yml`, so `-c` is always required (`rollback`, `status`, `create` too).
- Seeds (safe to re-run): `vendor/bin/phinx seed:run -c config/phinx.php` (or `-s ScriptTemplatesSeeder` for one). `ScriptTemplatesSeeder` writes the default wording from `src/Templates/DefaultTemplates.php` and **updates existing rows — except templates edited in the app** (`script_templates.edited_at` set), so re-run it after changing the defaults. `SchoolsSeeder` just runs the team API sync, so it needs network access.
- Sync teams from the API: `php bin/sync-teams.php` (cron-safe; the app also auto-syncs at most hourly when `/schools` or `/games/new` loads).
- Tests: `vendor/bin/phpunit` (suite in `tests/`, covers the rendering engine and roster-URL guessing).
- Roster scraper: `php tests/scraper/run.php [fixture ...] [--json]` replays `tests/fixtures/roster-pages/*.html` through `public/js/scraper-core.js` in headless Chrome (dev box only).
- Lint a file: `php -l path/to/file.php` — but dev runs PHP 8.3, so also run `vendor/bin/phpcs` (PHPCompatibility, `phpcs.xml.dist`), which flags anything newer than production's PHP 7.2 (e.g. indented heredoc closing markers broke the first deploy).
- Dev server: `php -S localhost:8000 -t public public/index.php` — the explicit router script is required, otherwise PHP's built-in server 404s extension-looking URLs before they reach Slim. On the shared dev box it already runs as the `pa-script-dev.service` systemd unit on port 8002, against the `pa-script-postgres` Docker container; check those before starting anything new.

## Code layout

- `public/index.php` — Slim front controller (+ `public/.htaccess`, per server and gitignored — copy `public/.htaccess.example`). Production serves the app from a subfolder (athletics.willamette.edu/pa), so never write a bare root-relative URL: templates use `<?= $this->base() ?>/games` / `$this->asset()`, PHP uses `App\View\Url::to()`, JS takes URLs from `data-*` attributes or form actions. The base path is `APP_BASE_PATH`, else detected from `SCRIPT_NAME`; `public/css/app.css` (single plain-CSS stylesheet), `public/js/` (teleprompter, `scraper-core.js` roster parser, `roster-import.js`).
- `src/Roster/` — `RosterUrlGuesser` (suggests a program's roster URL from the school's site + CMS provider), `RosterPageFetcher` (server-side fetch, public hosts only).
- `src/Routes/routes.php` — all routes; `src/Repository/` — one PDO repository per table; `src/Rendering/` — `TemplateRenderer`, `PlaceholderRegistry`, `GameContextBuilder`.
- `templates/` — `.phtml` views wrapped by `templates/layout.phtml`.
- `migrations/`, `seeds/` — Phinx.

Sport-specific roster options are flags on `sports` (`uses_batting_order` — Baseball/Softball's roster page swaps the Starter checkbox for a per-game Bat slot (`batting_order` 1–9) and Playing position (`lineup_position`, else the roster position is read), batting slot 10 (`GameRosterRepository::FLEX_SLOT`) is the starter who doesn't bat, read last — Softball's "In the flex at …" (`uses_flex`) or Baseball's "The starting pitcher, from …" ("SP"), `uses_libero` — Volleyball's per-game Libero checkbox, read "At libero" and last), not sport-name checks in code. Umpires are read by role via `officials.umpireList` ("Plate" → "behind the plate", "Field"/"Bases" → "covering the bases", "1B" → "at first base").

Players are always listed by jersey number (numeric compare on the digits, unnumbered last) — there is deliberately no manual player sort field. Coaches and officials keep a `sort_order`.

## What this is

A web app for Willamette University Athletics PA announcers that replaces a library of hand-edited Google Sheets (one per sport) used to run PA scripts at home games. Today, team names, coach names, officials, and starting lineups are retyped by hand into a narrated script before every game — this app makes rosters/coaches/games structured data and generates the presentable script (including a teleprompter mode) from that data instead.

A companion browser bookmarklet scrapes an opponent's roster off a live roster page (e.g. Sidearm Sports platform) instead of the announcer typing 20-30 names in by hand.

## Tech stack (target, per PLAN.md)

- **PHP 7.2 + Composer**, deployed to an existing RHEL server. No Node/JS build pipeline — plain PHP + vanilla JS only, so local dev and RHEL deploy are shape-identical.
- **Slim 4** as router/micro-framework.
- **Plain `.phtml` templates** (`<?php ?>` + `htmlspecialchars`), not Twig — deliberately avoided due to Twig 3's PHP ≥7.2.5 requirement being too close to the server's stated PHP 7.2.
- **PDO (`pdo_pgsql`)** direct to Postgres with prepared statements behind small repository classes. No ORM.
- **Phinx** for Postgres migrations.
- **Vanilla JS** for interactive bits: inline roster-editor fields via small `fetch` calls to JSON endpoints, and the teleprompter's auto-scroll (`requestAnimationFrame`, no library).
- **One shared password, no usernames** (`App\Auth\PasswordGate` middleware, `APP_PASSWORD` in `.env`; unset = off, as in dev). `/login` sets a 30-day cookie holding an HMAC of the password, so changing it logs everyone out; `fetch` requests get a 401 instead of a redirect. Exempt: `/login` and the bookmarklet's cross-site endpoints, which are gated by the shared `IMPORT_TOKEN` (embedded in the generated bookmarklet URL) instead — keep `PasswordGate::OPEN_PATHS` in step with production's `.htaccess` exemption. **Admin password** (`App\Auth\AdminGate`, `ADMIN_PASSWORD`; unset = open): a second shared password, checked inside PasswordGate, for the template pages — `/templates*`, `/snippets*`, `/sports/{id}/default-venue` (`AdminGate::ADMIN_PATHS`; add new template-editing routes there). `/admin/login` sets a 7-day `pa_script_admin` cookie (same HMAC scheme), `POST /admin/logout` ("Lock admin") clears it; blocked fetches/POSTs get 403. The nav shows Templates only when unlocked, via `Renderer::share()` (`adminEnabled`/`adminUnlocked` in every view).
- Local dev: PHP's built-in server (`php -S localhost:8000`) against local/shared dev Postgres — no Docker/XAMPP required.

## Core architecture decisions (don't relitigate these)

- **Sports are gender-agnostic base entities** (Soccer, Basketball, Baseball, Softball, Volleyball, Lacrosse). "Men's"/"Women's" is a `division` — a small extensible lookup attached to a sport's teams/templates, not a separate top-level sport. Adding a division (co-ed, JV, ...) must never require restructuring the sport list.
- **One flexible template engine, not one template per sport.** Sport-specific differences (batting order vs. simple starters, role-specific officials phrasing, neutral-site framing, per-division pronouns) are expressed as **data/config** via block-based script templates, never as code forks or new schema.
- **Script templates vary along two independent axes**: `division_id` (whose pronouns/phrasing) and `site_variant` (`home` vs. `neutral`). E.g. soccer is 3 `script_templates` rows: (Soccer, Women's, home), (Soccer, Men's, home), (Soccer, null, neutral).
- **Template blocks** are JSON: `{type: text, content}` | `{type: placeholder, key}` | `{type: loop, over: starters|reserves|battingOrder|officials, template: [...]}` | `{type: when, key, equals?, then, else?}`. The `loop` block generalizes every sport's per-player lineup pattern, including baseball/softball's batting-order variant; `when` covers the sheets' `if(...)` wording switches (captain, conference, today's/tonight's, optional coach-line parts). 0 counts as set in `when` (jersey number 0).
- **Venue**: `meta.venue` is the game's typed venue, else (home games only) `sports.default_venue` (edited on `/templates`, initial values `DefaultTemplates::VENUES`); `meta.gameVenue` is only the typed one. `meta.teamName` is the game's `SportRepository::TEAMS` label ("Women's Soccer"), `meta.sport` the sport slug.
- **Spoken forms** (`App\Rendering\Spoken`) replace the sheets' Apps Script `FORMATPOS`/`FORMATCLASS`/`FORMATSTATE`: per-sport position words, class years ("Fy." → "first year"), state abbreviations, and names per the game's `name_display` (`name` / `pronunciation` — guide, else name, what the sheets read / `both` — "Name (GUIDE)", the default for new games, `Spoken::DEFAULT_NAME_DISPLAY`), chosen on the Script tab or teleprompter bar via `POST /games/{id}/name-display`. `GameContextBuilder` adds them to each player (`spokenPosition`, `spokenYear`, `spokenHometown`, `spokenName`) and derives `headCoach` (first title *starting* with "Head") and `assistantCoaches`. `GameContextBuilder::assemble()` is pure, for template tests without a DB.
- **Short forms** (`App\Rendering\Abbreviate`, for tight layouts like the printed roster): `year()` → "Fy."/"So."/"Jr."/"Sr."/"Gr." from any spelling, `hometown()` → AP-style state ("Portland, Ore."; AP's spelled-out states and countries untouched). Both normalize through `Spoken` first.
- **Source sheets**: the Script tab is all formulas over the Setup/Home/Away tabs — download the sheet as .xlsx (Drive connector) and read the formulas, not the Drive text view, which only samples rows.
- **Placeholder resolvers are a static PHP registry** (key → resolver function against a render context), not a DB table — only promote to DB-editable if a future template editor genuinely needs runtime-added placeholders.
- **The app owns its data; nothing syncs live from Google Sheets.** Rosters/coaches are edited in-app and differ every game.
- **Rosters exist only per game** (supersedes PLAN.md's persistent-roster design, removed 2026-10-08 because the two kinds of roster confused users). Each game side gets an empty roster (`game_roster_snapshots` + `game_roster_players`/`game_roster_coaches`) filled by a roster-URL fetch, the bookmarklet, or by hand. There are no standing `players`/`coaches` tables. A `program` (school × sport × division) is internal only: games point at one per side, and it remembers that team's `roster_url` for the next game. Don't reintroduce a user-facing standing roster.
- **Bookmarklet scrapes always land in staging first.** `scraper.js` POSTs to `/api/import/stage.php`, which writes an `import_batches` row. Nothing touches real roster tables until a human explicitly reviews and commits via `/import/review.php?batch={id}`. The bookmarklet itself is a thin loader (just carries the token); the actual scraping logic lives in server-hosted `scraper.js` so it can be fixed/updated without redistributing the bookmarklet.
- **Officials are normalized** (`officials` table: name, role, sort_order), not a flat string, so the renderer can produce correctly-punctuated "X, Y, and Z" lists and support baseball/softball's role-specific umpire phrasing ("behind the plate", "at first base", ...).

## Data model summary

See PLAN.md's "Data model" section for full column lists. Key tables:
- `sports`, `divisions`, `schools`, `programs` (school×sport×division; internal — game sides + saved `roster_url`).
- `schools` is a read-only local cache of the athletics Team Data API (`TEAMS_API_URL`; https://github.com/chrissabato/opponent-api), keyed by the API's `slug` (stable; names get edited). Only `App\Teams\TeamApiSync` writes it; teams are edited in the API's admin, never in this app. Sync keeps a team the API dropped if a program still references it. Find the home school by slug (`App\Site::homeTeamSlug()` — `HOME_TEAM_SLUG`, Willamette's `willamette-university`), not by name — the API also has a `willamette-university-gold` alt-logo entry with the same short name. Schools with different men's/women's mascots have one entry per `variant` ("Men"/"Women", e.g. Cal Lutheran Kingsmen/Regals); pickers label them via `SchoolRepository::label()`, and game creation swaps to the entry matching the game's division (`SchoolRepository::forDivision()`).
- `games`, `game_roster_snapshots`, `game_roster_players`, `game_roster_coaches`, `officials` — per-game data; the only rosters.
- `script_templates` (sport_id, division_id nullable, site_variant, content_blocks JSONB) — the template engine.
- `import_batches` — bookmarklet scrape staging.

## Routes

All defined in `src/Routes/routes.php`:
- `/login` (`GET`/`POST`, `?next=`), `POST /logout`
- `/` — dashboard (upcoming games); `/schools` (read-only teams from the API), `POST /schools/sync`
- `/games`, `/games/new` (one "Team" dropdown — `SportRepository::TEAMS`, e.g. `soccer/womens` — gives the game's sport + division; add a team there), `/games/{id}` (`POST` with `_method=DELETE` deletes), `POST /games/{id}/details` (time, venue, conference, no-anthem, special announcement before the anthem, closing announcement at the end; the form autosaves), `POST /games/{id}/status` (Draft/Ready, `GameRepository::STATUSES`; the header badge is the picker), `/games/{id}/officials`, `/games/{id}/roster/{home|away}` (+ `/players`, `/coaches`), `/games/{id}/script` (+ `/customize`: edit a copy saved as `games.custom_script`, shown instead of the generated script by the Script tab and teleprompter; `/reset` clears it), `/games/{id}/teleprompter`, `/games/{id}/print` (portrait, teams side by side; `?starters=1`)
- `/templates` (list of templates, global snippets and each sport's default venue — `POST /sports/{id}/default-venue`, autosaved), `POST /snippets` (new snippet), `/snippets/{id}` (same editor, + `/preview`, `/reset`, `_method=DELETE` only when no template/snippet uses it — `App\Templates\Blocks::usesSnippet`), `/templates/{id}` (template editor, `POST` saves and sets `edited_at`; `/preview` JSON-renders unsaved text against a game; `/reset` restores `DefaultTemplates` and clears `edited_at`). The editor shows blocks as tag text (`App\Templates\TemplateSyntax`, round-trips exactly — pinned by `tests/Templates/TemplateSyntaxTest.php`): `{field}` placeholder, `[if field]…[else]…[/if]` / `[if field = value]` when, `[each list]…[/each]` loop, `[snippet Name]` snippet block (`script_snippets`, rendered in place by `TemplateRenderer`, which takes the snippets by name — always build it with `ScriptSnippetRepository::blocksByName()`); friendly names from `App\Templates\FieldCatalog` (a name maps separately to its value/test/list key), raw dotted keys also accepted. Add a FieldCatalog entry when templates need a new context key. `public/js/template-editor.js` colours tags with a `<pre>` mirror under a transparent-text textarea — keep their CSS box/font identical.
- `/bookmarklet`, `/bookmarklet/scraper.js`, `/api/import/stage` (token-gated), `/import/review/{batchId}` (+ `/commit`, `/discard`; `?game_id=&side=` preselects)
- Fill in from a document (panel on each game roster page): `POST /games/{id}/roster/{side}/fill` uploads a PDF/.docx, Gemini (`App\Fill\RosterFiller` + `GeminiClient`, `GEMINI_API_KEY`, `GEMINI_MODEL` default `gemini-3.5-flash-lite` + minimal thinking — matched `gemini-3.8-flash` on a real guide in ~3 s vs 1–3 min) suggests values for **blank** fields only (pronunciation, position, year, hometown; coach pronunciation, pronoun, seasons), shown on a review page; `/fill/apply` saves the ticked ones via `GameRosterRepository::fillPlayerField`/`fillCoachField`, which never overwrite. PDFs go to Gemini as inline data; .docx is unzipped by hand with zlib (`App\Fill\DocumentText`) because production PHP has no zip extension. Nothing is stored between upload and apply.
- Roster URL import (panel on each game roster page): `POST /programs/{programId}/roster-url`, `POST /roster/fetch` (server fetches the page, browser parses players + coaches with `scraper-core.js`, following a separate coaches page when the roster page has none), `POST /import/stage` (in-app staging → review). Bot-blocked sites fall back to the bookmarklet or pasted HTML — keep those fallbacks even though production is expected to be allowlisted by Presto.

## Build order

Follow PLAN.md's phased build order: (1) scaffolding — Composer/Slim/Phinx wired to Postgres with one page round-tripping the DB; (2) core schema + template engine proven end-to-end on Soccer (including the neutral-site variant); (3) extend to remaining sports as data/config, not new architecture; (4) teleprompter; (5) bookmarklet + import pipeline; (6) deploy to the RHEL server. Each phase has an explicit verification step in the plan (structural diff against real captured sheet text) — follow it rather than eyeballing.

## Verification approach

- `php -S localhost:8000` for interactive browser exercise at every phase; `psql` or a lightweight admin view to eyeball seeded/committed rows.
- Seed fixtures should encode the real sheet text captured during planning (quoted in PLAN.md per sport) — the pass/fail bar is "reseed, load the page, confirm the rendered script structurally matches the original."
- PHPUnit tests on the template-rendering engine specifically (block resolution, loop expansion including batting order, missing-placeholder handling) are worth prioritizing since every sport depends on this engine.
- The bookmarklet should be tested against a saved static HTML fixture of a representative roster page for repeatable local testing, with occasional live spot-checks against markup drift.

## Dev environment vs. production

**The current build/dev environment is not the production RHEL server** and will have tools, PHP extensions, and versions production does not. Don't assume something works in production just because it works here — verify anything environment-sensitive (PHP extensions, CLI tools, PHP/Postgres versions, Composer packages with native extension dependencies) against the actual RHEL server — see the production versions under Project status. Dev runs PHP 8.3 and Postgres 15, so run `vendor/bin/phpcs` and avoid post-9.3 SQL.
